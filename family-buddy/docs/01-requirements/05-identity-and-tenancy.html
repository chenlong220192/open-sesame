05 身份、租户与权限 Identity, Tenancy & Access Control

源文件docs/01-requirements/05-identity-and-tenancy.md 项目family-buddy 阶段调研 · 需求分析

你明确要求"SaaS 形态、可给很多家庭使用、家庭管理员能灵活定制家庭成员"。本文把这句话拆成可实施的需求。

这是全项目风险最高的模块：做错不是功能不好用，而是数据泄露。

一、三层身份模型

平台 Platform
  └── 租户 / 家庭 Household（数据隔离边界）
        ├── 成员 Member（家庭内的身份，可无账号）
        │     └── 账号 Account（可登录的凭据，0..1）
        └── 角色 Role（权限点集合，可自定义）

关键设计约束（P0）

  1. 成员 ≠ 账号。幼儿、部分长辈是"成员"但没有"账号"。所有业务数据挂在成员上，不挂在账号上。
  2. 一个账号在一个家庭内最多对应一个成员。
  3. 租户是强制边界：所有业务数据都必须有租户归属，无例外。

二、多租户需求

ID 需求 优先级 验收要点
FR-D15-01 家庭注册与创建 P0 注册即创建家庭，创建者为家庭管理员；家庭有不可变唯一 ID
FR-D15-08 租户数据隔离 P0 见下文第三节，为硬性要求
FR-D15-XX 邀请成员 P0 邀请码/链接含有效期与使用次数限制；接受后方可入家庭
FR-D15-XX 家庭成员上限 P1 可配置上限（防止滥用）；默认值待定（Q-003）
FR-D15-XX 家庭状态机 P1 试用 / 正常 / 停用 / 注销中 / 已注销；状态变更需留痕
FR-D15-XX 家庭设置 P0 家庭名称、地区、时区、币种、单位制、语言
FR-D15-XX 多家庭归属 待定 是否允许一个账号属于多个家庭 → Q-006

租户隔离的硬性要求（不可协商）

# 要求 验收方式
T1 任何业务查询都必须携带租户上下文 代码审查 + 必须有统一的机制，不依赖开发者自觉
T2 未携带租户上下文的查询必须默认拒绝，而非返回全部 单元测试覆盖
T3 必须存在跨租户越权测试 用家庭 A 的凭据请求家庭 B 的资源，断言 404/403
T4 租户上下文不得来自客户端可篡改的参数 只允许由服务端从会话/令牌解析
T5 附件下载同样受租户校验 直链不可绕过鉴权
T6 日志与导出不得跨租户泄漏 导出接口必须校验租户归属

三、账号与认证

ID 需求 优先级 验收要点
FR-D15-02 注册 P0 手机号或邮箱注册；需验证码/邮件验证（具体方式 Q-002）
FR-D15-02 登录 / 登出 P0 登录失败需限流与锁定；登出需使会话失效
FR-D15-03 密码策略 P0 最小长度与复杂度；禁止弱密码；使用标准哈希算法，禁止自研
FR-D15-03 密码找回 P0 通过验证渠道重置；重置链接一次性且有有效期
FR-D15-04 二次验证（2FA） P1 支持 TOTP；管理员账号建议强制
FR-D15-05 第三方登录 P1 微信/其他；需处理与已有账号的绑定
FR-D15-XX 会话管理 P0 可查看已登录设备并远程下线
FR-D15-XX 登录安全 P0 连续失败锁定、异地登录提醒、异常登录审计

硬约束：认证与加密不得自研。使用 Spring Security 体系内的成熟实现。这条写进需求是为了防止未来的你图省事手写。

四、角色与权限模型

4.1 权限模型的要求

ID 需求 优先级 验收要点
FR-D15-06 内置角色模板 P0 提供 4 类模板：家庭管理员 / 普通成员 / 受限成员 / 只读访客（定义见 02 文档）
FR-D15-06 自定义角色 P0 家庭管理员可基于模板调整权限点，或新建角色
FR-D15-06 权限点粒度 P0 粒度至少到"域 × 操作"（如 health:record:write）
FR-D15-07 数据范围控制 P0 每个权限点可限定数据范围：仅本人 / 指定成员 / 全家
FR-D15-07 成员间可见性 P0 可按"信息域 × 成员"设置可见性；含全隐藏与部分字段隐藏
FR-D15-XX 权限变更生效 P0 权限变更后旧会话不得继续持有旧权限
FR-D15-XX 越权防护 P0 前端隐藏菜单不等于后端拒绝；后端必须独立校验

4.2 三个维度的组合（授权模型核心）

最终是否允许 = 功能权限(功能点) AND 数据范围(能操作谁的数据) AND 可见性(能看到谁的数据)

必须覆盖的真实场景（写成验收用例）

场景 期望行为
成年子女不希望父母看到自己的体检异常 父母侧该成员的体检记录不可见，而非仅入口隐藏
配偶看不到某笔支出 该账户/该笔记录对配偶完全不可见，且统计中不出现该笔金额
孩子不能看到家庭财务 受限成员角色默认无 D04 任何权限
访客只能看日历 访客登录后除日历外无任何入口，且接口返回 403
管理员想改密码但看不到配偶密码 系统不应存在"查看他人密码"的能力

默认值问题：成员间可见性默认"互相可见"还是"默认仅本人可见"？这是安全与体验的取舍，见 Q-005。技术建议默认最严格（仅本人 + 管理员），由管理员显式放开 —— 因为家庭场景里"信息被家人看到"同样会造成真实伤害，而事后无法挽回。

五、大屏设备的身份

大屏无法用账号密码登录，需要独立的设备授权流程。

ID 需求 优先级 验收要点
FR-D14-01 设备配对码 P0 大屏首次打开显示一次性短码，管理员登录后在 Web 端确认授权
FR-D14-XX 设备令牌 P0 设备持有长期令牌；仅能拉取"已授权的卡片数据"
FR-D14-XX 设备权限最小化 P0 设备令牌不得具备任何写权限与账号管理权限
FR-D14-XX 设备管理 P0 管理员可查看在线设备并远程撤销授权
FR-D14-XX 设备令牌轮换 P1 支持主动轮换；撤销后立即失效

大屏是物理暴露的终端（客厅、来客可见）。因此设备令牌必须被视为"低信任凭据"：即使被拿到，也只能读到已脱敏的卡片数据。

六、数据合规（PIPL 相关）

SaaS + 健康/财务/证件数据 + 可能包含未成年人 → 属敏感个人信息范畴。以下为需求条目，具体实施方案留到架构与法务评审。

ID 需求 优先级 说明
NFR-COMP-01 告知同意 P0 注册与邀请成员时提供隐私政策，明确采集范围与用途
NFR-COMP-02 最小必要 P0 只采集功能必需字段；身份证号等非必需字段应改为可选
NFR-COMP-03 未成年人数据 P0 由监护人代管；采集范围最小化
NFR-COMP-04 查阅与更正权 P0 成员可查看与修改自己的全部数据
NFR-COMP-05 数据可携带 P0 可导出全部自有数据（结构化格式）
NFR-COMP-06 删除权与注销 P0 家庭注销后数据在约定期限内彻底删除，且需有可验证的删除记录
NFR-COMP-07 敏感字段加密 P0 证件号、卡号等字段级加密
NFR-COMP-08 访问审计 P0 敏感数据的访问与导出留痕
NFR-COMP-09 数据泄露应急 P1 有明确的止损与通知流程
NFR-COMP-10 数据存储地 P1 境内存储（若使用境内云，此项天然满足）

诚实声明：以上是需求层面的清单，不等于合规。正式对外提供服务前，需要根据实际业务形态做一次合规评审。本阶段不展开法律结论。
