编号 Q-0XX。每项包含：问题 / 为什么重要 / 选项 / 不决定的后果 / 我的建议。 状态取值：待你回答 / 已关闭 / 已移交架构阶段。

本清单不关闭，需求阶段不算结束（见 00-meta/roadmap.md 准出条件）。 我的建议只是建议，不是结论 —— 最终由你定。

Q-001 是否存在商业化（套餐/计费/支付）

  • 为什么重要：直接决定是否要引入套餐、配额、计费、发票、退款等一整套体系，是数量级的差异。
  • 选项：A. 纯自用 + 亲友免费；B. 免费公测，暂不收费；C. 明确要收费（需单独立项）
  • 不决定的后果：数据模型里缺少"套餐/配额"概念，后期补代价大；但过早引入则是纯浪费。
  • 建议：选 B（免费公测）。但预留配额字段（如家庭成员数上限、附件容量上限），留出但不实现计费。
  • 状态：待你回答

Q-002 注册与验证方式

  • 为什么重要：决定是否需要短信通道（实名认证 + 按条计费 + 模板备案），影响成本与上线门槛。
  • 选项：A. 手机号 + 短信验证码（体验好，有成本和备案门槛）；B. 邮箱 + 邮件验证（几乎零成本，国内用户感知略差）；C. 仅邀请制（管理员生成邀请码，不开自助注册）
  • 不决定的后果：无法开始做账号模块。
  • 建议：早期选 B 或 C。C 最省事且对"亲友家庭"场景完全够用，还能有效防止滥用。短信留到确需大规模外部分发时再上。
  • 状态：待你回答

Q-003 家庭成员上限与配额

  • 为什么重要：涉及防滥用与存储成本。
  • 建议：默认成员上限 20，附件容量 5GB/家庭，均可配置。数值仅为工程建议，不是结论。
  • 状态：待你回答

Q-004 大屏目标电视的型号与浏览器内核 ★最高优先级

  • 为什么重要：这是全项目最大的技术不确定性。 大屏方案（能否用现代 Vue 3 构建产物、是否需要降级、是否需要改用其它终端）完全取决于目标电视的浏览器能力。在未实测前，任何方案都是猜测。
  • 需要你提供：
    1. 电视的具体品牌型号
    2. 电视自带浏览器的内核版本（电视上打开 about:version 或访问 UA 检测页可查）
    3. 电视是否能安装第三方浏览器（如通过应用商店 / U 盘安装）
    4. 是否考虑改用电视盒子（如带较新 Chromium 的 Android TV 盒子）——通常比电视自带浏览器可靠得多
    5. 是否要求开机自动启动
  • 不决定的后果：架构阶段无法定前端方案；可能出现"写完发现电视打不开"的最坏情况。
  • 建议：进入架构阶段的第一件事就是实测这件事，最好在写任何前端代码之前。若电视浏览器过旧，可直接改用电视盒子，成本很低且能规避大部分兼容性问题。
  • 状态：待你回答

Q-005 成员间可见性的默认值

  • 为什么重要：安全与体验的直接取舍，且事后无法挽回（数据一旦被家人看到就收不回了）。
  • 选项：A. 默认互相可见（体验好，符合"一家人不分彼此"的直觉）；B. 默认仅本人 + 管理员可见（最严格）；C. 按域设不同默认（健康/财务严格，日历/待办开放）
  • 不决定的后果：无法实现权限模块的默认值逻辑。
  • 建议：C。日历/待办/纪念日默认家庭共享（协作需要）；健康、财务、证件、薪酬默认仅本人 + 管理员（隐私需要）。这是一条技术建议，不是已验证结论；具体域清单可在功能设计阶段定。
  • 状态：待你回答

Q-006 一个账号能否属于多个家庭

  • 为什么重要：影响账号模型与登录后的"选择家庭"流程，属于难以事后修改的设计。
  • 选项：A. 一个账号只能属于一个家庭（模型简单）；B. 可属于多个家庭，登录后切换
  • 不决定的后果：数据模型需要重做。
  • 建议：技术上按 B 设计（多对多），交互上按 A 呈现（只有一个家庭时不显示切换器）。理由：模型改起来贵，交互改起来便宜；现实场景确实存在（子女同时管自己家和父母家）。
  • 状态：待你回答

Q-007 跨域数据归属冲突

  • 为什么重要：同一件事在多个域都能录入时，必然出现数据不一致（这是本项目最容易失控的地方）。
  • 已知冲突：
    数据 可能归属 建议唯一归属
    社保公积金账户余额 D02 工作 / D04 财务 缴纳记录归 D02，资金余额归 D04
    房贷/车贷 D04 / D05 归 D04 负债；D05 只引用
    保险 D04 / D05 归 D04；车辆保险在 D05 展示视图
    会员订阅 D04 / D11 归 D04 账单与订阅
    水电物业费 D04 / D06 户号归 D06，缴费流水归 D04
    儿童成长数据 D03 / D08 归 D03，D08 引用
  • 建议：上表作为功能设计阶段的强制约束，逐个确认。原则：一个数据只有一个可写入口。
  • 状态：待你回答（是否接受上述归属方案）

Q-008 同上（并入 Q-007）

Q-009 v1 首批业务域与 v1 边界

  • 为什么重要：决定接下来所有工作的范围。
  • 建议方案：见 08-scope-and-phasing.md 第二节。摘要：
    • 底座 + D01 + D13 附件 + 通用能力
    • 业务域首批：D03 健康 / D04 财务（记账+账单+负债）/ D07 日历与提醒 / D11-01 证件到期 / D02 任职与薪酬
    • 大屏只做 4 张卡
  • 需要你回答：
    1. 是否接受这个首批范围？
    2. D10 人情往来（还礼提醒）成本低价值高，是否提前到 v1？
    3. 大屏只有 4 张卡是否可接受？
  • 状态：待你回答

Q-010 是否做"D13-02 重要信息保管"（密码类）

  • 为什么重要：存密码是高风险功能。做不好就是给全家数据装了个后门。
  • 选项：A. v1 不做，引导用专业密码管理器；B. 做，但强加密 + 二次确认 + 全量审计
  • 建议：A（v1 不做）。理由：单人业余开发的项目，承担"保管密码"的责任不划算；一旦出事后果极重。若确有需求，见 Q-010 的 B 方案需要在功能设计阶段专门论证。
  • 状态：待你回答

Q-011 平台运营是否需要应急数据访问通道

  • 为什么重要：SaaS 运营上，客服有时需要看用户数据排查问题；但这与"运营者不应读业务数据"的原则冲突。
  • 选项：A. 完全不开放（安全最好，但排障只能靠日志）；B. 开放但需用户显式授权 + 全程留痕 + 数据自动脱敏
  • 建议：早期（你既是运营也是开发者）选 A，因为你能直接查数据库。等真有外部用户且真有客服角色时再考虑 B。
  • 状态：待你回答

Q-012 大屏需要的外部数据源

  • 为什么重要：每个外部 API 都是一份成本 + 一个可能失效的依赖。
  • 需要确认：天气（用哪家？免费额度够吗？）、快递物流、新闻、股市
  • 建议：v1 天气也先不做（见 08 文档大屏最小版）。若要做，选免费额度足够且无强制实名的源，并做好失效降级。
  • 状态：待你回答

Q-013 相册照片的来源

  • 为什么重要：决定是否需要手机相册同步（实现成本不低）还是仅支持手动上传。
  • 选项：A. 仅手动上传；B. 手机相册自动同步（需要移动端，属远期）
  • 建议：v1 选 A，且不做相册卡片（08 文档已排除）。相册留到移动端立项时一起做。
  • 状态：待你回答

Q-014 月度云成本上限

  • 为什么重要：决定服务器规格、是否上对象存储、是否上托管数据库。
  • 建议：需要你给一个数字。早期建议尽量低（最低配云主机 + 本地磁盘或廉价对象存储），把成本留给真正需要的地方。
  • 状态：待你回答

Q-015 数据保留与注销后的删除期限

  • 为什么重要：合规要求"注销后删除"，但"立即删除"与"保留一段时间以防误操作"需要平衡。
  • 建议：注销后进入 30 天冷静期（可撤销），期满后彻底删除，并保留删除操作记录（不含业务数据）。此建议为工程建议，合规层面需后续评审。
  • 状态：待你回答

Q-016 记账的录入负担与形态

  • 为什么重要：记账功能最常见的失败原因不是功能不够，而是家人不录。
  • 选项：A. 完整逐笔流水记账；B. 只记大额与固定支出 + 月度汇总；C. 只记固定负债与账单（房贷/订阅），不做日常记账
  • 建议：v1 选 B 或 C 起步。先把**固定支出（房贷、账单、订阅）**管起来 —— 这部分少而重要，录入成本低，价值立即可见。逐笔记账等有真实需求再加。
  • 状态：待你回答

Q-017 通知渠道

  • 为什么重要：短信需企业实名、模板备案、按条付费；微信模板消息需公众号/服务号主体。
  • 选项：A. 仅站内通知（零成本，但"到点提醒"价值大打折扣 —— 没人主动打开就收不到）；B. 邮件（成本低，国内查看频率低）；C. 短信（触达最好，有身份与费用门槛）；D. 微信（需公众号）
  • 建议：早期选 A + B；若"到期提醒"是你的核心诉求（很可能是），则 C 值得投入 —— 因为提醒不触达等于没有提醒。这一项需要在功能设计前定。
  • 状态：待你回答
