ADR-0001 采用单仓库多项目（monorepo）组织方式

源文件docs/00-meta/decisions/ADR-0001-monorepo-layout.md 项目family-buddy 阶段调研 · 需求分析
本页目录
  • 背景
  • 决策
  • 备选方案与取舍
  • 后果
  • 状态：已接受
  • 日期：2026-10-01
  • 决策者：项目所有者
  • 影响范围：仓库结构、CI、文档归属、发布流程

背景

项目包含后端服务、前端 Web、大量文档，未来可能还有移动端与运维脚本。需要一个仓库组织方式，且当前只有一个 GitHub 私有仓库 family-buddy。

决策

单仓库多项目。根目录下并列：

family-buddy/
├── docs/        文档（需求/设计/架构/API）
├── backend/     后端工程（独立可构建）
└── frontend/    前端工程（独立可构建）

backend/ 与 frontend/ 各自拥有独立的构建体系（Maven / npm），互不依赖，可单独构建、单独部署。

备选方案与取舍

方案 优点 缺点 采纳
单仓库多项目 文档与代码同源；一次 commit 完成跨端改动；CI 集中；重构（改字段）时前后端同步率最高 仓库体积随时间增长；需配置按路径触发 CI 避免全量构建 ✅
双仓库（前后端各一） 权限与发布完全隔离；仓库小 「改一个接口」要跨两次提交、两次 PR，早期单人开发收益低；文档归属尴尬 ❌
三仓库 + submodule 隔离最彻底 submodule 日常操作成本高、易出错；单人开发严重过度设计 ❌

后果

  • 正面：早期开发（大量跨端改动）成本最低；文档不会与代码脱节。
  • 成本：需在 CI 中做路径过滤（backend/** 变更才跑后端流水线），否则构建浪费。此配置留到工程初始化阶段。
  • 预留退路：任一子目录后续可独立拆仓（git subtree split / git filter-repo）。拆分成本随时间上升，故本决策需在进入开发前确认，之后不再复议。
  • 移动端将来若立项，作为第四个并列目录加入，不改变本决策。
