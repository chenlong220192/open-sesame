Software Requirements Specification

本文档集定义 Health Buddy（健康伙伴） 的建设目标、用户角色、信息模型、 能力范围、非功能需求与风险登记。产品定位为面向家庭的 AI 健康伙伴 —— 用户上传医疗报告、医院单据、病历照片，系统落盘后经 OCR 与 AI 结构化解读， 为每一位家庭成员生成专属、持续演进的健康视图。

当前阶段：需求分析进行中。功能设计与架构设计尚未开始， 相关结论以本说明书为准，未定事项统一登记于「待调研项」。

01 · 愿景与范围

状态：草案 v0.1 · 阶段：需求分析 · 不涉及功能设计与架构

1. 一句话定位

Health Buddy 是一个面向家庭的 AI 健康伙伴：用户上传医疗报告、医院单据、病历照片，系统自动 OCR 识别与 AI 解读，为每一位家庭成员生成专属、持续演进的健康视图。

2. 要解决的问题

# 痛点 现状 本产品的回应
P1 家庭医疗资料散落 纸质单据进抽屉、照片散在相册、PDF 丢在微信文件传输助手 统一落盘为结构化的成员健康档案
P2 看不懂报告 检验单上几十个指标，只有箭头，不明含义 AI 解读：指标含义 + 异常提示 + 通俗说明
P3 没有纵向对比 单张报告是快照，看不出「比上次好还是差」 时序指标追踪 + 趋势可视化
P4 数据不属于自己 数据锁在各家医院公众号、App 里 数据归用户，原件可导出
P5 记不住要做的事 复查时间、吃药、打疫苗全靠脑子 主动提醒（伙伴感的核心）
P6 家里老人的档案没人管 子女想管，但没工具 单账户多成员，一人管全家

3. 产品目标（本期）

目标 可验收的判据
G1 建立家庭健康档案 一个账户可创建 ≥ 2 个家庭成员，各自数据互不串扰
G2 打通上传到呈现的主链路 上传一张检验单照片，无需人工录入即可在档案中看到结构化指标
G3 让用户看得懂 每条异常指标有中文通俗解释
G4 让用户看得到趋势 同一指标 ≥ 2 次测量后可看到趋势
G5 提供专属大屏 每个家庭可自定义大屏展示内容与布局

4. 产品非目标（明确不做）

非目标 理由
不做电子病历（EMR） 面向医疗机构的产品形态完全不同，本产品无医生、无处方权
不做在线问诊 涉及互联网医院资质，非软件问题
不做医学诊断 AI 输出仅作信息整理与科普，不构成医疗建议 —— 这是必须写进用户协议的红线
不做多租户 账户本身即数据边界（见 D-005）
不做移动端 App 远期规划（见 D-011）
一期不做运营数据大屏 二期做（见 D-009）
一期不做硬件/可穿戴对接 数据来源聚焦「用户上传」，设备接入另立议题

2. 一期能力详述（边界级，非设计级）

C1 账户与认证

  • 要能：手机号或邮箱注册、登录、登出、找回密码、修改密码、查看与编辑个人昵称头像。
  • 边界：不做第三方登录；不做实名认证；不做 MFA。

C2 家庭成员管理

  • 要能：一个账户创建 1~N 个成员；编辑成员基本信息；标注与本人关系；归档成员；删除成员（级联处理其数据，需二次确认）。
  • 边界：不做成员授权（一期）；家庭成员的证件号一期不采集。

C3 原件上传与落盘

  • 要能：上传 jpg/png/heic/pdf；单文件大小有上限；上传即落盘并生成可追溯记录；相同文件（哈希一致）识别为重复并提示；查看原件；删除原件（需考虑级联影响）。
  • 边界：不做批量上传（一期）；不做邮件/微信导入。

C4 OCR 识别

  • 要能：识别中文医疗单据文本；给出整体与逐块置信度；多页 PDF 逐页处理。
  • 边界：不承诺 100% 准确率；低质量图片需给出「识别质量差，建议重拍」的明确反馈而非静默失败。

C5 AI 结构化抽取

  • 要能：自动判断单据类型（检验单 / 处方 / 病历 / 发票……）；抽取该类型对应的字段；给出逐字段置信度；将可归一的字段映射到主数据。
  • 边界：一期不追求覆盖所有单据类型，先做强 2~3 类（建议：检验报告 + 处方/用药 + 门诊病历）。

C6 AI 解读

  • 要能：对异常指标给出通俗中文解释（「这个指标是什么、偏高意味着什么、通常建议怎么办」）。
  • 边界（红线，见风险 R-002）：
  • ❌ 不做诊断
  • ❌ 不给用药建议
  • ❌ 不替代医生
  • ✅ 输出必须带明确免责声明
  • ✅ 必须可追溯到依据（至少标明是科普性说明）

C7 人工确认与修正

  • 要能：查看某条数据来自哪个原件、哪一步处理、置信度多少；修正抽错的字段；修正后保留原值与修正历史。
  • 边界：不做多人协同审核（一期）。

C8 健康档案浏览

  • 要能：
  • 时间轴视图：按时间倒序列出所有事件
  • 类别视图：按就诊/用药/检验/影像/疫苗等分类
  • 指标视图：按单个指标看历次记录
  • 边界：一期不做全文检索。

C9 时序指标追踪

  • 要能：任一指标只要有 ≥2 次记录即可画趋势；标注正常参考区间；标记异常点；点击数据点可回溯到来源报告。
  • 边界：不做预测（一期）。

C10 用户健康大屏

  • 要能：
  • 预置 ≥3 套默认大屏模板（如「长者关怀」「儿童成长」「慢病管理」）
  • 从卡片库中挑选卡片、拖拽排列、调整尺寸
  • 按成员切换大屏
  • 保存多套配置
  • 边界：不做大屏共享（一期）；不做用户自制卡片模板（一期）。

C11 提醒 / 待办 ⚠️

  • 要能：手工创建提醒；关联到成员与具体记录；到期提示；标记完成。
  • 建议：一期保留。这是「健康伙伴」定位最直接的落点，且实现成本不高。
  • 边界：智能推断（AI 从「3 个月后复查」自动生成提醒）放二期。

C12 健康目标 ⚠️

  • 要能：设定目标指标与目标值；自动计算进度。
  • 建议：一期可裁剪。

C13 数据导出 ⚠️

  • 要能：导出成员档案为可读格式。
  • 建议：至少支持「导出原始文件包」，成本低且是用户信任来源。

C14 系统管理员后台

  • 要能：账户查询 / 禁用 / 启用 / 重置密码；主数据（医院、科室、检验项目、药品、疾病）CRUD；审计日志查询。
  • 边界（硬约束）：管理员不可查看任何用户健康数据。

4. 一期建议交付顺序

按「主链路先通」原则，不作为排期承诺：

阶段 A：地基
  账户与认证 + 家庭成员管理 + 系统管理员后台骨架

阶段 B：主链路（最关键的验证点）
  原件上传落盘 → 处理任务状态机 → OCR → AI 结构化

阶段 C：价值呈现
  档案浏览 + 人工确认修正 + 时序趋势

阶段 D：伙伴感
  用户健康大屏（预置模板）→ 大屏自定义 → 提醒

阶段 E：打磨
  导出、异常反馈、性能与体验优化

核心判断：阶段 B 是整条链路风险最高的部分（OCR 与 AI 的准确率、单据类型覆盖面、成本），应尽早打通端到端最小可用版本，用真实单据验证可行性，再决定后续投入。不要等前端做完了才发现识别效果不达标。

OW-001 · 数据库选型

为什么需要单独讨论：本项目存在两种截然不同的数据形态（见 >信息模型 §3.0）：

  • 关系型数据：账户、成员、就诊、用药、单据等
  • 时序数据：体征指标（血压、血糖、体重……）会长期高频增长，且查询模式以「按时间范围取序列」为主

候选方向

方案 优点 缺点
PostgreSQL 单一库 运维简单；JSONB 灵活；可用分区表处理时序 时序查询性能需自行优化
PostgreSQL + TimescaleDB 时序与关系库统一 引入扩展，运维复杂度上升
PostgreSQL + 独立时序库（InfluxDB 等） 时序性能最优 双存储、一致性复杂，原型期过度设计
MySQL 生态熟悉 时序与 JSON 支持弱于 PG

调研要点 1. 原型期数据量预估与年增长量 2. 时序数据量级（一个家庭 5 人 × 每人 10 指标 × 每天 1 次 ≈ 1.8 万点/年/家庭） 3. 是否需要跨家庭聚合分析（影响选型） 4. 倾向（未验证）：原型期用 PostgreSQL 单库 + 分区表，时序量级上来后再评估 TimescaleDB。属建议，需实测验证。

OW-002 · 对象存储方案

医疗原件（照片、PDF）体量大、不可变、需鉴权访问，适合对象存储而非数据库或本地文件系统。

方案 适用场景
本地磁盘 / NAS 个人原型期，最简单
MinIO（自建 S3 兼容） 想保持数据自控，又能用 S3 生态
云 OSS / COS / S3 商业化阶段，弹性与可靠性好

# 能力 要求

OW-007 · 大屏方案 ← 用户明确处于调研阶段

大屏是两个独立产品，需分别调研，但可能共用渲染技术：

用户健康大屏（一期） 运营数据大屏（二期）
使用者 注册用户 运营人员
数据源 单个家庭的健康数据 全平台统计数据
核心价值 看懂家人健康，看到趋势 看懂平台运转，发现异常
交互 可拖拽配置、多套保存、响应式 全屏常驻、自动轮播、固定 1920×1080
指标来源 用户档案数据 埋点/统计聚合

需要先澄清的产品问题（未确认，建议先想清楚再选技术）

  1. 「可定制」到哪一步？ - L1 只换数据范围（选成员、选时间区间） - L2 换卡片组合（从卡片库挑选、拖拽排列） - L3 换卡片样式与参数（颜色、阈值、聚合方式） - L4 用户自制卡片（写 SQL / 表达式） → 定级直接决定实现成本，建议一期做到 L2，L3 部分支持。

  2. 布局方式：自由拖拽（画布坐标）还是栅格布局（12 栅格）？建议栅格 —— 自由布局在响应式下必然崩坏。

  3. 是否区分「大屏」与「仪表盘」的视觉风格？用户侧应偏「温暖、可读、生活化」，运营侧偏「深色、信息密集、动效」。

  4. 是否需要「大屏分享」（生成只读链接给家人看）？

技术调研要点

项 需查清
图表库 ECharts / Chart.js / D3 —— 医疗时序图的参考区间带、异常点标注支持度

OW-010 · 是否采纳 FHIR R4 作为内部信息模型

当前倾向：不采纳为内部模型，仅作为未来互操作时的映射目标。 理由：FHIR 完整实现复杂度极高，对单人原型项目是过度设计。但信息模型设计时借鉴其资源划分（>信息模型 §8 已做映射），成本低收益高。

需确认。若未来有与医院/机构对接的计划，需重新评估。

OW-011 · 异步任务框架选型

OCR/AI 处理必须异步（NFR-P-05）。需调研：

选项 说明
Spring @Async + 数据库状态机 最简单，够用；缺点是重启丢任务、无重试保障
Spring Integration / Spring Batch 偏批处理，与事件驱动的单据处理不完全匹配
Quartz + 数据库任务表 成熟，支持持久化与重试
消息队列（RabbitMQ / Kafka）+ Worker 最可扩展；原型期偏重
轻量持久化队列（如数据库轮询表） 折中方案

调研要点 1. 是否需要在应用重启后恢复未完成任务？（建议需要 —— 用户上传后系统重启导致任务丢失，体验极差） 2. 重试策略与死信处理 3. 是否引入独立 Worker 进程（为未来水平扩展预留）
